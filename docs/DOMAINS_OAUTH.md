## Routing

`ops/caddy/dead-lock-de.caddy` defines the dead-lock.de snippets and HTTP/HTTPS sites. HTTPS `/` returns a local 302 to `/streamer/`, preserving the query. `/streamer*`, `/website*`, `/twitch/onboarding*` and `/twitch/faq*` retain the main domain's mounts of `/opt/deadlock/twitch/current/website/dist`, including its streamer asset 404 behavior, CSP, dynamic command/help/FAQ upstream, partner-profile import and legacy redirects. All local root and canonical website redirects preserve the complete query, including explicit `lang=de`. `/streamer` and `/streamer/index.html` redirect to `/streamer/`; `/streamer/v1` gains a trailing slash; `/streamer/v2`, `/streamer/v2/` and descendants redirect to `/streamer/`; `/streamer/onboarding` and `/streamer/onboarding/` redirect to `/twitch/onboarding`. Static sub-sites include `/streamer/faq/`, `/streamer/vergleich/`, `/streamer/onboarding/` and `/streamer/clips/`. As on the main domain, the bare `/streamer/faq` uses the dynamic upstream, not the static FAQ. The English host excludes `/streamer/clips` and `/streamer/clips/` from the profile import so the W2 static clips entry is not mistaken for a streamer named `clips`. `/twitch` and `/twitch/*` retain the public dashboard upstream and special handlers without changing the incoming Host header. Admin redirects, legal handlers, EventSub upstream, probe blockers and security headers remain intact. The community root, `/faq/`, `/clips/` contest and other non-website/non-dashboard paths still redirect to the main domain with 308; they are not mirrored. Legal pages retain their existing main-domain behavior at the same path.

OAuth starts and callbacks, including `/twitch/auth/*`, `/callback/*`, raid authorization, social-media OAuth and platform connects, return a 302 to the same path and query on the main domain. An absent `lang` parameter is appended as `lang=en`; existing hints and query bytes are preserved. EventSub is a webhook, not an OAuth callback. HTTP requests for `/`, `/streamer*`, `/website*`, `/twitch` and `/twitch/*` first return a 308 to the same English host over HTTPS, so no website/dashboard HTML, JavaScript or API response is served over plaintext. HTTP OAuth navigation goes directly to the main domain over HTTPS with a 302. Other paths return a 308 to the main domain, except the existing common probe blockers. Social OAuth disconnect endpoints are mutation APIs, not OAuth navigation: they remain on the dashboard upstream and retain their POST method.

## Language and navigation

Resolution order is valid `lang=en|de` query, saved `dashboard.language.v2` choice, a legacy `dashboard.language` value (reset to German on the main domain, ignored on the English host), English-host default, then the browser fallback (German when any preferred browser language is German, otherwise English). The provider saves the resolved language on every load, so the first-visit detection runs only once. It removes only `lang` from the current URL, retaining other parameters and the fragment.

Website host detection selects English on both English hosts for every built entry, including legacy and affiliate entries, unless `lang=de` is explicit. Main-domain language defaults are unchanged. W1/W2 supply the existing translations; this routing package does not add translations to legacy pages.

Dashboard login/connect links on the English host use absolute main-domain URLs, never new provider redirect URIs. The selected language is added to the dashboard login and Discord-link flows' existing `next` parameter. `auth/oauth_login.rs:56` preserves allowed next-path queries and `handlers/auth_login.rs:451` returns that stored path after login. Discord linking stores `next_path` in existing broker metadata (`handlers/discord_link.rs:85`) and restores it on completion (`:177` and `:246`), preserving both the language query and account fragment. These successful flows can return to the main-domain dashboard with English selected.

### Unchanged-backend limitations

A bare `lang` on an OAuth start URL does not ensure language persistence through every provider round trip. `handlers/auth_login.rs:80` accepts only `next` at login start; a direct Caddy redirect without a language-bearing `next` therefore cannot preserve the hint. Raid callbacks use their existing destination (`handlers/auth_login.rs:599` and `:667`) without propagating a start-query language hint, and social-media callbacks build their destination in `handlers/social_media.rs:3803` and `:3807` without language state. These flows still use the main domain, but no new cross-domain cookie or guaranteed language propagation is implemented for them. Steam callbacks and Discord error fallbacks likewise remain unchanged. The frontend does not claim that an unused start-query hint changes provider state.

## Exact splice and validation steps

1. Make a full temporary copy of `~/repos/Caddy/hosts/v50671/Caddyfile`, leaving the live file untouched.
2. In that copy, replace the section starting at `(dead_lock_oauth_redirects) {` through the closing brace of `dead-lock.de, www.dead-lock.de { ... }` with the complete contents of `ops/caddy/dead-lock-de.caddy`. Leave every unrelated snippet and site block unchanged. Read the live file without printing authentication or credential directives.
3. Run `caddy adapt --config /tmp/ttb-opus-o2-Caddyfile --adapter caddyfile` and `caddy validate --config /tmp/ttb-opus-o2-Caddyfile --adapter caddyfile`. If the unprivileged validator cannot open existing production log writers, replace only their `output file` destinations in the temporary copy with unique `/tmp` log paths before validation. This does not alter the routing splice.
4. Deployment, copying into the Caddy repository checkout (`~/repos/Caddy`), and reload are integrator actions, not part of this package. No live Caddy change or reload was performed by the worker.
