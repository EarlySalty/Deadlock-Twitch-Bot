# Social-Media-Studio unification plan

## 1. Scope, evidence and acceptance

This is package U0, a plan only. Product code and production data are unchanged. The governing brief is `.tasks/2026-10-15-social-unify/AUFTRAG.md`. K1 is external to this package and is not planned again.

The target is one channel-owned pipeline: intake into one pool, preparation in one of three modes, optional human review, one schedule, destination-specific upload and verified outcome. AI permission, quality failures, platform connection and TikTok per-post consent are prerequisites, not additional publishing modes.

Acceptance is exactly one visible schedule, one clip collection and one three-way mode selector. Review is an independent control. All six mode/review combinations must reach a verified platform outcome using throwaway material. Existing approvals, metadata, schedules, TikTok drafts and publication history must remain traceable.

Important implementation findings:

1. Today the tabs are `Heute`, `Freigabe`, `Planen`, `Veröffentlicht`, `Einstellungen`. The old configuration is still mounted under `Neue Twitch-Clips` inside the B planning screen.
2. B's `ai_editing_enabled` and `ProductionMode::{Static,Ai}` do not represent three modes. Static currently renders a vertical layout; it is not literal original-file passthrough.

4. The B executor unconditionally holds TikTok with `tiktok_effect_boundary_pending`; its capability is false. Removing that hold alone is unsafe. `PlatformPublisher` uses `upload_video`, whereas TikTok needs the existing checkpointed transfer and status reconciliation.
5. `social_produced_videos.metadata.platforms` already carries per-platform copy, but `ai_editor/metadata.rs` permits only AI videos and currently editable review versions. Legacy copy also exists in enrichment, source fields and queued payloads.
6. Current cross-table slot triggers and unique indexes enforce a shared channel/time slot. Per-platform schedules need a deliberate replacement, not just an extra platform selector.

### 3.3 Unified execution and publishing

The canonical state progression is source available, preparing, ready, optional review, reserved/scheduled, uploading, destination verified, aggregate published. Exceptional conditions remain named and actionable. Source rows and versions are not alternative publication queues.

The planner selects from the pool, creates a job and destination reservations atomically. Preparation downloads/probes once, creates the exact artifact, resolves metadata and freezes the job's effective policy. Review saves decisions for the selected version/platforms. Review-off eligible work receives explicit policy authorization, not a forged user decision. A file/text/account change before upload invalidates the affected binding; once an effect starts the payload is immutable.

`autopilot_publish::PublishExecutor` becomes the only new-work publisher. Refactor common credential, checkpoint and status logic out of `upload_worker.rs` rather than copying its old conversion-and-approval path into B. Runtime `main.rs` must not start two consumers for unified rows. During rollout the legacy worker may drain unmapped legacy claims only, behind an explicit predicate; after cutover remove its new-work startup while keeping shared uploader helpers.

- **YouTube:** use channel-bound credentials, the frozen exact file/copy and existing uploader. Persist the returned video ID before considering the target uploaded; confirm processing and actual visibility. Private or unlisted is reported as such, never public success. Unknown request outcomes must not trigger blind fresh uploads.
- **TikTok:** replace the unconditional B hold only when exact-version consent validation, creator restrictions and checkpoint support are wired. Pass `TikTokPostOptions` to the existing uploader, persist the returned `publish_id` before byte transfer, and reconcile status after transfer/restart using the same operation. Distinguish initialized, transferring, processing, inbox, failed, uncertain and verified publication. A publish ID alone is not a published video ID. No fresh init after an uncertain transfer; expose the recovery action/reason on the row.
- **Instagram:** use the same produced artifact and caption snapshot. Preserve container/media identifiers needed to reconcile asynchronous creation/publishing. Confirm the resulting Reel/media and account visibility. Reconcile a lost response before retrying publication; do not create a duplicate container/post on an unknown outcome.
- **All three:** preserve generation fencing, idempotency, account binding, pause/reauth checks, per-destination retries and quota delays. One failed destination does not replay completed ones. Retention cannot remove an artifact needed by a pending, failed or uncertain destination. A channel-wide `published` badge cannot conceal a destination hold.

No renderer or metadata generator runs inside the upload effect. Every uploader consumes the same selected version and its platform payload. `social_produced_videos.status` is an aggregate projection; queue result rows retain the destination truth.

## 5. One schedule model

Configuration remains in `social_media_autopilot_settings`:

- Scope `shared`: one normalized list of `{weekday, local_time}` entries applies to selected platforms. Multiple entries for a weekday are supported, for example Monday `08:00` and `22:00`.
- Scope `per_platform`: each selected platform has its own list using the same shape. Switching to shared previews any differing schedules and requires choosing the retained pattern; never union or discard differences silently. Switching to per-platform copies the shared pattern as editable values.
- ISO weekdays 1 through 7, strict `HH:MM`, normalized sort and deduplication within the same scope. Do not retain the UI's current 28-row ceiling if it would truncate migrated data; preserve oversized existing settings and surface validation rather than silently saving fewer entries.
- The canonical timezone comes from channel administration. A schedule API returns the effective timezone read-only. Timezone changes affect future unreserved slots, not committed UTC times without an explicit replan.
- Preserve current DST behavior: skip nonexistent wall times, choose one deterministic occurrence for an ambiguous wall time, never double post. Test Europe/Berlin transitions. No missed-slot catch-up burst.
- Keep lead time and pause semantics. Reservations are made transactionally under the owner lock. Shared schedules reserve all intended destinations at one time for the same selected clip. Per-platform clip allocation is Q5; do not infer it from the mere presence of three schedules.
- Replace the current channel/time-only unique indexes and `social_production_guard_shared_slot` with destination-scoped reservation guards in a new migration. A single production job/video may serve several platform due times. Its `scheduled_at` becomes a production/reference deadline, not the destination scheduler. Publication execution/completion must therefore be destination-specific; the current video-wide `publication_executed_at` cannot prevent a later platform's due event.
- Schedule display, `Heute` next event and upload dispatch all derive from these reservations and queue rows. The legacy cadence planner no longer allocates new slots after cutover.

## 8. Questions for the user

1. **Q1: May AI-edited videos publish without routine human review?** The mode description says review before publishing, but orthogonal review and six-cell acceptance require an off combination.
